01 · Summary

One application, one boundary

Create apps/ai-window as an independently runnable and packageable Electron workspace named @lightcode/ai-window, with the product name Lightcode AI.

Independent application

Own Electron main, preload, React renderer, packaging configuration, icons, dependencies, and tests.

Owned backend

Run the existing tRPC backend as a managed Electron utility child process with an authenticated ephemeral endpoint.

Launcher-only editor

Stop embedding the AI renderer. Keep the editor button temporarily and launch or focus Lightcode AI through lightcode-ai://open.

Data continuity

Continue using ~/.lightcode/state.db so existing projects, threads, and messages remain available.

02 · Architecture

A clean runtime boundary

The renderer talks only through a narrow preload surface. Electron owns the server lifecycle, while the server remains isolated in a utility process and exposes a short-lived loopback tRPC endpoint.

Renderer React AI application Queries, streaming, projects, and threads
Electron Main + preload Window, protocol, connection, and lifecycle
Utility process tRPC + Codex backend 127.0.0.1, ephemeral port, session token
The desktop editor is outside this runtime chain. Its temporary button opens lightcode-ai://open. It does not load the AI renderer, import the router, own the database, or supervise the server.

04 · Implementation

Nine implementation phases

Each phase ends with a coherent boundary and leaves no unresolved implementation choice.

01

Scaffold the independent workspace

  • Add apps/ai-window to the root npm workspaces and TypeScript project references.
  • Create package @lightcode/ai-window with product name Lightcode AI, bundle ID com.m4nik1.lightcode-ai, executable name lightcode-ai, and Windows package name lightcode_ai.
  • Give it independent dev, typecheck, test, package, and make scripts.
  • Add root aliases npm run ai-window, npm run package:ai-window, and npm run make:ai-window.
  • Copy the current Lightcode icon assets into the new workspace so builds do not depend on desktop-owned files.
  • Configure Forge to build four entries: Electron main, preload, React renderer, and a Node-targeted server.js bundle.
  • Use a normal native frame on Windows and Linux. Preserve the hidden macOS title bar and traffic-light spacing used by the current AI UI.
02

Move the AI renderer

Move the following from desktop into apps/ai-window/src/renderer:

  • AIWindow.tsx and the complete components/AIWindow directory.
  • useAIChat.tsx.
  • aiModelConfig.ts, consolidated into src/shared.
  • The textarea, dropdown, shimmer, and class-name utilities used by the AI UI.
  • AI-specific Tailwind, fonts, animation, Markdown, and theme CSS.
  • The tRPC client bootstrap.

Create a dedicated renderer entry containing only React strict mode, the AI API/query provider, AiChatProvider, and the AI window component. Do not carry over EditorTabsProvider, editor components, file-tree types, or editor styling.

Relocate apps/desktop/ai-window-react.html into an AI-app documentation folder and mark it as a legacy reference rather than runtime code.

03

Move and embed the backend

  • Move the contents of apps/server into apps/ai-window/src/server.
  • Remove the standalone @lightcode/server workspace and root server script.
  • Keep the existing tRPC procedures and their request/response shapes: queryAI, getThreadTitle, stopTurn, loadMessages, addProject, addThread, deleteThread, getThreads, and getProjects.
  • Remove the unused greeting procedure.
  • Declare @lightcode/codex-protocol as an explicit workspace dependency of Lightcode AI.
  • Use one src/shared/aiModelConfig.ts definition for renderer and backend model IDs and reasoning effort.
  • Refactor server creation into a function that accepts configuration and returns a closable HTTP server.

Required compilation corrections

  • Remove the stray token following the ThreadService constructor.
  • Await Codex client initialization during backend startup.
  • Narrow completed thread items by their discriminant before reading agent-message fields.
  • Close the Codex app-server client during backend shutdown.
04

Manage the server as an Electron child process

  • After Electron becomes ready, launch the bundled server.js with utilityProcess.fork.
  • Bind the child only to 127.0.0.1 and request port 0, allowing the OS to choose an unused port.
  • Open the existing database, then send a typed readiness message containing the selected port.
  • Generate a random per-launch bearer token in the parent, pass it through the child environment, and require it on every tRPC request.
  • Pass the actual Vite renderer origin during development and null for the packaged file:// renderer. Permit the authorization header in CORS responses.
  • Wait up to 15 seconds for readiness before creating the BrowserWindow; show a Retry/Quit dialog on failure.
  • If the backend exits unexpectedly, attempt one automatic restart, reload the renderer after reconnecting, and show Retry/Quit if the restart also fails.
  • On shutdown, close the HTTP server, database, and Codex client before terminating the utility process.
backendMessages.ts 
type BackendReadyMessage = {
  type: "backend-ready";
  port: number;
};

type BackendErrorMessage = {
  type: "backend-error";
  message: string;
};
05

Add a narrow preload boundary

  • getBackendConnection returns the current child-process endpoint and session token.
  • selectProjectDirectory returns one selected directory path or null, not Electron’s complete dialog result.
  • Do not expose general file reading, file writing, editor, or desktop-window-launch APIs.
  • Construct the tRPC client only after retrieving the backend connection.
  • Pass the bearer token through httpBatchStreamLink headers.
  • Provide the initialized query client and typed tRPC runtime through an AI-specific React context.
AI preload API 
type BackendConnection = {
  baseUrl: string;
  token: string;
};

type LightcodeAIAPI = {
  getBackendConnection(): Promise<BackendConnection>;
  selectProjectDirectory(): Promise<string | null>;
};
06

Preserve the existing database

  • Continue using ~/.lightcode/state.db.
  • Create ~/.lightcode recursively before opening the database.
  • Preserve the existing tables and data without schema changes.
  • Make the database path injectable for tests while keeping the current location as the production default.
  • Do not copy, rename, or delete the user’s database.
  • Ensure only the Lightcode AI backend owns the database connection after separation.
07

Register and handle lightcode-ai://

  • Register lightcode-ai in the packaged protocol metadata and call app.setAsDefaultProtocolClient with the correct development and packaged arguments.
  • Acquire app.requestSingleInstanceLock before starting the backend.
  • Handle macOS open-url, Windows/Linux protocol arguments, and Electron’s second-instance event.
  • Every lightcode-ai://open invocation restores and focuses the existing AI window.
  • Protocol invocations do not carry project, thread, or message payloads in this migration.
08

Convert desktop to a launcher-only bridge

  • Remove the query-parameter renderer switch, createAIWindow, --ai-window, and the second BrowserWindow path.
  • Remove the AI UI, chat context, model configuration, tRPC client, AI-only UI primitives, and AI-only providers from desktop.
  • Implement the main-process launch handler with shell.openExternal("lightcode-ai://open").
  • Keep the current macOS and non-macOS “AI window” buttons, but make them call launchAIApp.
  • If launching fails, display an editor-owned dialog explaining that Lightcode AI must be installed or started.
  • Remove desktop dependencies that become AI-only, including tRPC, React Query, Markdown, motion, Radix, AI icons, shadcn helpers, and font packages where no editor usage remains.
  • Remove the Tailwind Vite plugin and Tailwind imports if the remaining editor uses only plain CSS.
  • Remove stale tracked renderer output; generated artifacts remain ignored.
Desktop launcher contract 
type LaunchAIAppResult =
  | { ok: true }
  | { ok: false; reason: "not-installed" | "launch-failed" };

launchAIApp(): Promise<LaunchAIAppResult>;
09

Normalize TypeScript and workspace configuration

  • Configure the AI workspace for Vite-compatible ES modules and bundler resolution.
  • Add explicit Vite client and Node/Electron types where appropriate.
  • Update desktop TypeScript configuration so it no longer imports server source outside its root, rejects Vite CSS imports, or compiles Vite config files as CommonJS.
  • Guard the macOS dock API with isMac && app.dock.
  • Regenerate package-lock.json.
  • Require the root typecheck to pass for desktop, AI window, and codex-protocol.

06 · Verification

Tests and acceptance scenarios

Verification covers the workspace boundary, backend lifecycle, data compatibility, launcher behavior, and distributable artifacts.

Automated checks

  • npm install completes with the updated workspace graph.
  • npm run typecheck passes across every workspace.
  • The Lightcode AI renderer production build succeeds.
  • The Lightcode AI Forge package succeeds.
  • The desktop Forge package succeeds after AI dependencies are removed.
  • Backend tests use a temporary database.
  • Existing schema initialization and project, thread, and message persistence pass.
  • Missing or incorrect bearer tokens are rejected.
  • Authenticated tRPC requests succeed.
  • Port 0 resolves to a reachable loopback endpoint.
  • Startup and graceful shutdown close all resources.
  • Lifecycle tests cover ready, error, timeout, exit, and retry messages.

Manual integration

  • npm run ai-window starts the child backend and opens the AI UI.
  • Existing database projects, threads, and messages appear unchanged.
  • Folder selection, thread creation/deletion, streaming, titles, and interruption behave as before.
  • Closing Lightcode AI terminates its backend child.
  • Starting Lightcode AI twice focuses the existing instance.
  • The custom protocol restores a minimized or hidden window.
  • The desktop starts without Lightcode AI installed.
  • The desktop button launches or focuses Lightcode AI when installed.
  • A missing protocol handler produces a useful error.
  • Windows, macOS, and Linux packages contain the server bundle and icons.

07 · Rollout

A staged bridge, not a shared renderer

The temporary compatibility surface is deliberately small and can be removed without touching editor features.

Migration lands

The new app owns its renderer, backend, database connection, packaging, and single-instance lifecycle.

Temporary bridge remains

The editor retains only its visible button, launchAIApp preload method, and protocol-launch module. The old embedded renderer is removed.

Independent adoption

Lightcode AI is fully usable on its own and can be installed, started, focused, packaged, and tested without the editor.

Future cleanup

Once users launch Lightcode AI directly, remove the desktop button, launchAIApp IPC channel, and protocol-launch module.

08 · Boundaries

Assumptions and defaults

These decisions are fixed for this migration and should not be reopened during implementation.

01

Both applications remain in the current monorepo and share the root lockfile.

02

Lightcode AI is independently packaged and installed.

03

The existing icon is reused initially; new branding is out of scope.

04

The editor and AI application do not share renderer code after migration.

05

Existing AI behavior and the database schema are preserved. Feature redesign and unrelated chat fixes are out of scope.

06

The existing apps/server has no consumers other than the AI window and can be removed after its code moves.

07

The custom protocol is a temporary editor integration; Lightcode AI remains fully usable without the editor.
