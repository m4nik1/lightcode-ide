01 · Orientation

Overview

@lightcode/codex-protocol is the workspace’s narrow, typed boundary around the Codex app-server protocol. It starts the Codex CLI as a child process, exchanges newline-delimited JSON over standard I/O, correlates request responses, and presents the supported thread and turn operations as ordinary TypeScript methods.

Client

Small typed surface

Connect, create or resume a thread, start or stream a turn, interrupt, subscribe, and close.

Schema

Generated definitions

Request, response, and notification types are emitted by the same pinned Codex CLI version.

Transport

Internal JSONL

The package owns process spawning, JSON envelopes, request IDs, timeouts, stderr, and shutdown.

The package is private, is not published to npm, requires Node.js 20 or newer, and is ESM-only. It intentionally pins @openai/codex to 0.140.0 and initializes the stable protocol with experimentalApi: false.

Boundary, not application framework The typed client is the public runtime abstraction. Generated types are the compile-time contract. The JSONL transport remains internal and is not exported from the package root.

Source: package manifest, root exports, and transport implementation.

02 · Workspace setup

Installation

Consume the package through the repository workspace. There is no registry release and no separate binary to install: the exact Codex CLI is already a direct package dependency.

package.json 
{
  "dependencies": {
    "@lightcode/codex-protocol": "workspace:*"
  }
}

The package’s prepare script runs npm run build, producing dist during workspace installation. Build output is reproducible and intentionally not source-controlled.

03 · First connection

Quick start

Construct the client with an identifying clientInfo object, connect once, inspect the typed initialization response, and always close the child process in finally.

connect.ts 
import {
  CodexAppServerClient,
  CODEX_PROTOCOL_VERSION,
  type InitializeResponse,
} from "@lightcode/codex-protocol";

const client = new CodexAppServerClient({
  clientInfo: {
    name: "lightcode",
    title: "Lightcode",
    version: "1.0.0",
  },
});

try {
  const server: InitializeResponse = await client.connect();

  console.log(CODEX_PROTOCOL_VERSION); // "0.140.0"
  console.log(server.userAgent);
  console.log(server.codexHome);
  console.log(server.platformFamily, server.platformOs);
} finally {
  await client.close();
}
The handshake runs exactly once per live connection connect() starts codex app-server --stdio, sends initialize, awaits its response, then sends initialized. Concurrent or later calls reuse the same promise or cached InitializeResponse; they do not repeat the handshake.
04 · Process & state

Lifecycle

One client owns one local app-server process. The implementation keeps protocol stdout separate from diagnostic stderr and exposes only a small state machine to consumers.

01 Consumer Your Node.js app
→
02 Typed client Threads & turns
→
03 JSONL transport stdin / stdout
→
04 codex app-server --stdio

Connection states

disconnected → connecting → connected → closed
  • Before connection: thread and turn methods throw AppServerStateError.
  • Connection failure: state returns to disconnected, the process is closed, and a later connect() may try again.
  • Unexpected exit: pending requests fail with AppServerProcessError and the client returns to disconnected.
  • Explicit close: closed is terminal; connect() then rejects. Repeated close() calls are safe.
  • Close during a pending connect: the in-flight connect() rejects with AppServerProcessError, the client stays closed, and later connect() calls reject with AppServerStateError.

Shutdown

close() marks the client closed, ends child stdin, and waits for normal process exit. If the process has not exited after two seconds, the transport sends a kill signal and waits up to another 500 milliseconds. Process-exit listeners are notified, but explicit closure does not move the public state away from closed.

05 · Conversations

Thread operations

A thread is the persistent conversation boundary. Start one for new work or resume an existing ID, then carry the returned thread.id into every turn request.

threads.ts 
const started = await client.startThread({
  cwd: "/absolute/path/to/project",
  model: "gpt-5.5",
  sandbox: "workspace-write",
  approvalPolicy: "never",
});

const threadId = started.thread.id;

const resumed = await client.resumeThread({
  threadId,
  cwd: "/absolute/path/to/project",
});

console.log(resumed.thread.id); // same resumable thread identity

startThread() and resumeThread() return the server’s typed response, including the resolved model, provider, working directory, approval policy, sandbox policy, reasoning effort, instruction sources, and thread. The emitted ThreadResumeParams requires threadId and accepts configuration overrides; the public method passes that typed object through unchanged.

Thread configuration

Set model when starting a thread to choose its initial model. The same field on resumeThread() overrides the model of the resumed thread. Inspect the returned model, modelProvider, serviceTier, and reasoningEffort fields to see the settings the server resolved.

06 · Work units

Turn operations

Use startTurn() when you only need the immediate typed receipt. Use streamTurn() when you want the complete, filtered notification stream through terminal completion. Both methods accept the same TurnStartParams, including model and reasoning overrides.

Start a turn

start-turn.ts 
const receipt = await client.startTurn({
  threadId,
  model: "gpt-5.5",
  effort: "low",
  input: [
    {
      type: "text",
      text: "Summarize this repository.",
      text_elements: [],
    },
  ],
});

console.log(receipt.turn.id, receipt.turn.status);
Turn overrides persist model, effort, cwd, approval, sandbox, service-tier, summary, and personality overrides apply to this turn and subsequent turns on the thread. The reasoning field is named effort in this protocol, not modelReasoningEffort.

Stream through completion

stream-turn.ts 
for await (const notification of client.streamTurn({
  threadId,
  input: [
    {
      type: "text",
      text: "Summarize this repository.",
      text_elements: [],
    },
  ],
})) {
  switch (notification.method) {
    case "item/agentMessage/delta":
      process.stdout.write(notification.params.delta);
      break;
    case "turn/completed":
      console.log(notification.params.turn.status);
      break;
  }
}
1

Subscribe first

The client installs its notification listener before it sends turn/start.

2

Retain early events

Same-thread notifications arriving before the start receipt are held in the bounded early-event buffer.

3

Resolve the turn

After the receipt supplies turn.id, early and live events are filtered by both thread and turn.

4

Yield the terminal event

turn/completed is yielded to the consumer, then the async iterator ends and removes its listeners.

Interrupt an active turn

interrupt.ts 
await client.interruptTurn({
  threadId,
  turnId: "turn-id-from-turn-started",
});

The interrupt method awaits the server’s turn/interrupt response and resolves void. Observe the turn’s subsequent notifications to determine its final status.

07 · Events

Typed notifications

onNotification() narrows listener parameters from the literal method name. The returned function removes the listener, so subscriptions can be scoped to a component, request, or feature.

notifications.ts 
const unsubscribe = client.onNotification(
  "turn/started",
  ({ threadId, turn }) => {
    // threadId: string; turn: Turn
    console.log("turn started", threadId, turn.id);
  },
);

// Later: stop receiving this method.
unsubscribe();
thread/started thread/status/changed turn/started turn/completed turn/plan/updated item/started item/agentMessage/delta item/completed error warning
Global subscription

onNotification()

Receives one named method from every thread and turn until you unsubscribe. It does not buffer or correlate events.

Turn-scoped iterator

streamTurn()

Starts a turn, retains early events, filters by thread and turn, applies a bounded buffer, and ends after completion.

Listener exceptions are reported through onError() and do not stop the stdout reader. Diagnostic callbacks are isolated as well: an exception thrown inside an error listener is ignored so protocol processing can continue.

09 · Failure model

Errors and failure behavior

All package-specific errors inherit from AppServerError. RPC and lifecycle failures reject the relevant operation; diagnostic protocol failures and fail-closed server requests are also emitted to onError().

Exported error classes
Error classWhen it occursUseful fields
AppServerError Base class for all exported app-server-specific errors. name, message
AppServerStateError Wrong client/transport state, or a non-positive/non-integer notification capacity. message
AppServerProtocolError Invalid JSON, non-object or unrecognized envelope, unknown response ID. payload
AppServerRpcError The server returns an RPC error object for a pending request. method, requestId, code, data
AppServerTimeoutError No RPC response arrives within requestTimeoutMs. method, requestId, timeoutMs
AppServerProcessError The child fails to start, exits, terminates while work is pending, or its stdin pipe errors mid-write. exitCode, signal, optional cause
UnsupportedServerRequestError The server initiates a request without a safe built-in response. method
ServerRequestRejectedError A known approval, elicitation, input, or tool request is answered fail-closed. method
NotificationBufferOverflowError A streamTurn() early/live queue reaches capacity before the consumer drains it. capacity

Observe diagnostics and stderr

diagnostics.ts 
const stopErrors = client.onError((error) => {
  console.error(error.name, error.message);
});

const stopLogs = client.onStderr((text) => {
  process.stderr.write(text);
});

// Clean up subscriptions when their owner is disposed.
stopErrors();
stopLogs();
  • Malformed stdout is reported and skipped; it does not crash the line reader.
  • Errors on the child’s stdin pipe (for example EPIPE when the process dies mid-write) are wrapped in AppServerProcessError and emitted to onError() instead of surfacing as an uncaught stream error.
  • RPC timeouts remove the pending request. The client does not automatically retry it.
  • A process exit rejects every pending request and fails any active streamTurn() queue.
  • Stderr is never parsed as protocol JSON and is only delivered to onStderr().

Authoritative definitions: errors.ts.

10 · Fail closed

Server-initiated requests

App-server communication is bidirectional, but this package deliberately has no interactive approval surface. The transport answers every server request immediately with either a safe negative result or an unsupported-method error.

Built-in server request responses
Server methodResponse
item/commandExecution/requestApproval Decline.
item/fileChange/requestApproval Decline.
applyPatchApproval Denied with a non-interactive-client rejection reason.
execCommandApproval Denied with a non-interactive-client rejection reason.
mcpServer/elicitation/request Cancel with null content and metadata.
item/tool/requestUserInput Return an empty answers object.
item/tool/call Return no content items and success: false.
item/permissions/requestApproval RPC error -32601 and UnsupportedServerRequestError.
account/chatgptAuthTokens/refresh RPC error -32601 and UnsupportedServerRequestError.
attestation/generate RPC error -32601 and UnsupportedServerRequestError.
Any other method RPC error -32601 and UnsupportedServerRequestError.
No request is intentionally left unanswered Known interactive operations are declined, denied, cancelled, or completed with an empty negative response. Unknown operations receive an explicit unsupported-request response. Both paths emit a typed diagnostic error to subscribers.
11 · Type surface

Generated protocol types

The root package entry point re-exports the common types needed by the typed client. The two protocol subpaths expose the complete generated schema for consumers that need lower-level unions or richer response models.

import type {
  ClientRequest,

  Thread,

} from "@lightcode/codex-protocol/protocol/v2";
Root exports

Common client types

ClientInfo, InitializeResponse, ServerNotification, thread/turn params and responses, options, and state.

Full schema

Generated unions and models

The /protocol and /protocol/v2 barrels mirror the stable generator output from the pinned CLI.

The package asks Codex to generate its stable surface and does not enable the experimental API during initialization. Generated TypeScript supplies compile-time checking; at runtime the transport validates only the basic response, request, and notification envelope shapes. It does not perform full JSON Schema validation of every payload because the client and locally spawned CLI are version-matched.

Schema coverage versus client coverage

For protocol 0.140.0, the generated ClientRequest union contains 87 request methods and ServerNotification contains 67 notification methods. These include thread lifecycle and search, model discovery, configuration, filesystem, skills, plugins, MCP, account, command execution, reasoning, realtime, and sandbox operations. The notification chips above are representative rather than exhaustive; use the generated unions for the complete literal method list and correctly narrowed parameter types.

Generated types do not add client methods CodexAppServerClient intentionally exposes only connection/initialization, thread start and resume, turn start and interrupt, streaming, subscriptions, and shutdown. Types such as ThreadForkParams, ModelListParams, or TurnSteerParams describe the wire protocol but are not callable through a public generic request method in this package.
Type-only imports are intentional Generated modules contain type declarations rather than runtime validators. Use import type when importing from either protocol subpath.
12 · Version control

Protocol generation and version drift

Protocol definitions are generated by the exact Codex CLI the package depends on. The manifest, generation script, and exported CODEX_PROTOCOL_VERSION all pin 0.140.0.

shell 
# Regenerate checked-in protocol definitions.
npm run generate -w @lightcode/codex-protocol

# Generate into a temporary directory and compare for drift.
npm run protocol:check -w @lightcode/codex-protocol
1

Update both pins

Change the exact @openai/codex dependency and PINNED_CODEX_VERSION in scripts/generate.mjs.

2

Generate stable definitions

The script runs codex app-server generate-ts from the resolved package CLI.

3

Normalize for Node ESM

Relative generated imports receive explicit .js or /index.js specifiers.

4

Check drift

The check compares all files and verifies src/version.ts without replacing the checked-in directory.

Never edit src/generated manually Regeneration replaces the generated directory as a unit. Hand edits will either disappear on the next run or fail the drift check.

Source: generate.mjs and check-generated.mjs.

13 · Verification

Testing and troubleshooting

shell 
# Compile dist.
npm run build -w @lightcode/codex-protocol

# Check package source without emitting.
npm run typecheck -w @lightcode/codex-protocol

# Build, then run transport, client, and consumer-compile tests.
npm test -w @lightcode/codex-protocol

# Verify generated files match the pinned CLI.
npm run protocol:check -w @lightcode/codex-protocol

# Optional: initialize and close the real local app-server.
npm run test:smoke -w @lightcode/codex-protocol

The smoke test only initializes and closes the real process; it does not create a thread. The regular test suite also compiles built-package consumers under both NodeNext and Bundler module resolution.

14 · Explicit non-goals

Package boundaries

This first package version stays deliberately small. Its omissions are part of the contract, not missing setup steps.

Not included

No application policy

The server application consumes this package, but ownership, persistence, model selection, and UI behavior remain application concerns.

Not included

No WebSocket transport

The only transport is a locally spawned app-server using newline-delimited JSON over stdio.

Not included

No experimental API

The initialize handshake explicitly sends experimentalApi: false; generation uses the stable surface.

Not included

No auth or approval UI

The package does not authenticate users, render prompts, or accept approvals. Interactive requests fail closed.

Not included

No npm publication

The manifest is private. Other packages consume it through the repository workspace.

Not included

No full runtime schema validation

Runtime checks validate envelope shape, while generated TypeScript checks payload structure at compile time.
