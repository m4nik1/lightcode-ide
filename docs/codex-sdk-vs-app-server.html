Codex SDK vs. Codex App Server

Two ways to embed OpenAI's Codex agent in your own coding app — one is a typed library for automation, the other is the full protocol that powers Codex's own clients. Which one should your AI coding app build on?

The short version

Same binary, two entry points

Both are modes of the same codex CLI binary — installing it gives you exec, the SDK, and app-server at once. The difference is the contract each exposes to your app.

@openai/codex-sdk

Codex SDK

A TypeScript library (Node 18+) that spawns the CLI and exchanges JSONL events over stdio. Typed threads, turns, and events as ordinary async functions.

  • Threads & resume — startThread() / resumeThread(id); sessions persist in ~/.codex/sessions
  • Streaming — runStreamed() yields an async generator of structured events (tool calls, file changes, usage)
  • Structured output — JSON responses conforming to a schema you supply per turn
  • Images — mix text + local images in one turn
  • Safety knobs — sandbox mode, approval policy, working directory
codex app-server

Codex App Server

A bidirectional JSON-RPC 2.0 server (stdio, Unix socket, or experimental WebSocket) — the same interface that powers the VS Code extension, desktop app, and Codex Web.

  • Full client surface — auth, conversation history, approvals, streamed agent events
  • Interactive approvals — server pauses a turn and asks your UI to allow/deny before proceeding
  • Mid-turn injection — send messages into a running turn; persistent threads
  • Language-agnostic — anything that can spawn a child process (Tauri, Electron, Python, Go)
  • Generated schemas — generate-ts / generate-json-schema emit version-exact types

Developer experience

What integration looks like

The SDK is a function call; the app server is a session you drive.

Codex SDK — thread + streaming
import { Codex } from "@openai/codex-sdk";

const codex = new Codex();
const thread = codex.startThread();

const { events } = await thread.runStreamed("Fix the failing tests");
for await (const event of events) {
  if (event.type === "item.completed") render(event.item);
  if (event.type === "turn.completed") console.log(event.usage);
}
App Server — spawn, handshake, listen
# start the server (stdio default, or a socket)
codex app-server
codex app-server --listen ws://127.0.0.1:4500

# client flow (JSON-RPC 2.0):
# 1. send initialize → receive capabilities
# 2. send initialized notification
# 3. start a thread, start a turn
# 4. read streamed notifications; answer approval requests

# generate version-exact client types
codex app-server generate-ts --out ./schemas
Context

Why the app server exists

OpenAI first tried exposing Codex as an MCP server for the VS Code extension, but IDE-grade needs — streaming diffs, approval flows, thread persistence — didn't map cleanly onto MCP's tool-oriented model, so they built a dedicated protocol. Every official Codex surface (terminal, VS Code, macOS desktop, Codex Web) now runs through the same app-server process. Deployment patterns from those clients are reusable: bundle the binary and speak stdio locally (VS Code style), decouple client and server release cycles (Xcode style), or run it in a container and bridge to a browser over HTTP/SSE (Codex Web style). A complementary industry effort, Zed's Agent Client Protocol, aims at the same problem but as a vendor-neutral standard.

Recommendation

For an AI agent coding app

Default to the App Server if you're building a real client UI

If your app shows a chat/agent surface where users watch the agent work, review diffs, and approve commands — the app server is effectively the only choice. Interactive approval dialogs, mid-execution message injection, auth and history management, and the richest event stream all live there. It's the same contract OpenAI's own clients depend on, so it will keep pace with new features.

Choose the SDK instead if your "app" orchestrates Codex headlessly — CI jobs, batch refactors, a backend service that runs tasks and returns results. You get typed threads, streaming, structured output, and sandbox controls in a few lines, with none of the protocol plumbing.

Hybrid is legitimate: many teams ship the SDK first for backend automation, then adopt the app server when the product needs a live, interactive agent surface. Budget for the app server's experimental status — pin CLI versions and regenerate schemas per release.
