Event emitters and the Codex child process.

The transport layer is three ideas stacked: an OS pipe that delivers bytes with no message boundaries, a reassembler that turns those bytes back into JSON lines, and an emitter that hands each line to whoever cares. This page takes all three apart, then traces a single user query end to end.

Mechanics node:events node:child_process JSONL over stdio
Concept

An emitter is a subscription list, nothing more.

Most confusion about event emitters comes from imagining infrastructure that is not there. There is no queue, no broker, no delivery guarantee, no replay, no ordering across event names, and nothing crosses a process or thread boundary. An emitter is an object holding a map from string keys to arrays of functions.

The whole idea in one line

emit(name, arg) means "look up the array stored at name and call every function in it, right now, with arg."

The reason this pattern exists at all is that some things have no place to return to. A function call is a closed transaction: one question, one answer, and the caller is still on the stack waiting for it. But a child process streaming tokens for ninety seconds is not answering a question — it is producing an open-ended series of arrivals, at times nobody chose, possibly for an audience that did not exist when the work started. There is no stack frame left to return into.

An emitter inverts control to fit that shape. Instead of your code asking "what happened next?", you leave callbacks behind and let the runtime call them as things happen. That inversion is the entire value proposition, and every limitation below is the price of it.

01

Synchronous

emit() calls listeners inline and returns only after the last one finishes. It does not await async listeners; it collects a floating promise and moves on.

02

Amnesiac

No history is kept. A listener attached after an emission never learns it happened. Subscribe first, act second.

03

Unbuffered

No backpressure signal reaches the producer. If your consumer is slower than Codex, buffering and shedding are your job.

04

Unguarded

A throwing listener unwinds out of emit() into whatever called it — here, the protocol read loop for every session on the process.

A useful contrast

A Promise is a mailbox that holds exactly one letter and remembers it forever — subscribe whenever you like, you still get the value. An emitter is a doorbell: if nobody is standing there when it rings, the ring is simply gone. This single difference explains most emitter bugs in streaming code.

Implementation

The whole thing in thirty lines.

Reading a working reimplementation removes the mystery faster than any description. Node's EventEmitter adds warnings, symbol keys, and error semantics on top, but the core is exactly this.

TinyEmitter.ts
type Listener = (...args: unknown[]) => void;

export class TinyEmitter {
  private listeners = new Map<string, Listener[]>();

  on(name: string, fn: Listener) {
    const list = this.listeners.get(name) ?? [];
    list.push(fn);                       // append; order = registration order
    this.listeners.set(name, list);
    return this;                         // chainable, like Node's
  }

  off(name: string, fn: Listener) {
    const list = this.listeners.get(name);
    const index = list?.indexOf(fn) ?? -1;  // IDENTITY comparison — which is
    if (index >= 0) list!.splice(index, 1); // why you can never remove an
    return this;                            // inline arrow function.
  }

  once(name: string, fn: Listener) {
    const wrapper: Listener = (...args) => {
      this.off(name, wrapper);           // remove BEFORE calling, so a
      fn(...args);                        // throwing fn still unsubscribes
    };
    return this.on(name, wrapper);
  }

  emit(name: string, ...args: unknown[]) {
    const list = this.listeners.get(name);
    if (!list?.length) return false;      // no listener: the event is GONE
    for (const fn of [...list]) fn(...args); // copy: a listener may off() itself
    return true;                          // "someone heard it", not a result
  }
}

Three details in that code are load-bearing in production:

  • off() compares by identity. rpc.on("notification", (m) => handle(m)) creates a function you no longer hold a reference to, so it can never be removed. Per-turn and per-client listeners must be named variables.
  • emit() iterates a copy. Without it, a listener that removes itself mid-emission would shift the array under the loop and skip its neighbour. Node does the same.
  • The return value is not a result. true only means the array was non-empty. If you need to know whether work actually succeeded, that must travel back through a Promise or another event — never through emit().

Practice

The five calls you will actually write.

api-in-anger.ts
// Long-lived: one per process, attached at construction, never removed.
rpc.on("notification", routeToSession);

// One-shot: fires at most once, cleans itself up.
rpc.once("exit", (error) => supervisor.scheduleRestart(error));

// Scoped: named so it can be removed. Anonymous inline functions here
// are the #1 source of listener leaks.
const perTurn = (msg: Notification) => { /* … */ };
rpc.on("notification", perTurn);
try { await runTurn(); } finally { rpc.off("notification", perTurn); }

// Instrumentation: export this as a gauge. A number that only grows is a leak.
metrics.gauge("appserver.listeners", rpc.listenerCount("notification"));

// Teardown: drop everything at once when a process is retired.
rpc.removeAllListeners();
Async listeners are a trap worth naming

rpc.on("notification", async (msg) => { await db.write(msg); }) looks fine and is not. emit() does not await it, so ordering across notifications is no longer guaranteed, and a rejection becomes an unhandled promise rejection rather than an error you can see. If a listener must do async work, have it push onto an explicit per-thread queue that a separate worker drains in order.

Operating system

What spawn actually creates.

spawn("codex", ["app-server"], { stdio: ["pipe", "pipe", "pipe"] }) asks the kernel for three unidirectional pipes, forks, and executes a genuinely separate program. Understanding that literally is what makes the rest of the design obvious.

Your Node processchild.stdin — Writable
child.stdout — Readable
child.stderr — Readable
↔
Three OS pipesKernel ring buffers, ~64 KB each. Byte-oriented, unidirectional, no framing, no typing. Full buffer = writer blocks.
↔
codex app-serverSeparate PID, own memory, own crash domain. Reads lines from fd 0, writes JSONL to fd 1, logs to fd 2.

No shared memory. No function you can call. No return value. The only channel between you and Codex is bytes in a pipe, arriving whenever the kernel schedules it — which is precisely why the read side has to be event-driven. Node surfaces pipe readability the only way it can inside an event loop: by emitting.

So you inherit a chain of emitters before writing any of your own, each wrapping the one below it and speaking a slightly higher-level language:

ObjectEmitsMeaning of its payload
childspawn, error, exit, closeProcess-level facts: it started, it could not start, it died, its pipes drained
child.stdoutdata, endArbitrary Buffer chunks — no relationship to message boundaries
child.stderrdataHuman logs. Never protocol. Keep it a separate pipe.
readline.Interfaceline, closeExactly one complete newline-terminated string per emission
AppServerRpcnotification, serverRequest, log, exit, protocolErrorProtocol meaning — the first layer that is about Codex rather than plumbing
Never merge stderr into stdout

A single panic message or progress bar written to a merged stream lands in the middle of your JSONL and breaks the parser for the rest of the process's life. Keep stdio[2] its own pipe and route it to your logger — after redaction, since Codex's logs can contain prompt content and paths.

The part that bites everyone

Bytes are not messages.

A pipe has no concept of a message. It delivers however many bytes happen to be available when you look. One data event can carry half a JSON object, or two and a half of them.

what-the-kernel-hands-you.txt
// Three 'data' events carrying three protocol messages — misaligned:

data #1  '{"method":"item/agentMessage/delta","params":{"delta":"This '
data #2  'repo is"}}\n{"method":"item/agentMessage/delta","params":{"del'
data #3  'ta":" a CLI tool"}}\n{"method":"turn/completed","params":{…}}\n'

// Chunk #1 is not valid JSON. Chunk #2 ends a message AND starts one.
// chunk.toString().split("\n").map(JSON.parse) throws on the first chunk
// and silently drops the tail of every chunk after it.

The fix is a reassembly buffer: append each chunk, then repeatedly slice off everything before the next newline. readline does exactly this, which is why the transport uses it — but writing it once makes the failure mode concrete:

manual-reassembly.ts
const MAX_LINE = 8 * 1024 * 1024;
let buffer = "";

// setEncoding matters: without it you concatenate Buffers, and a chunk
// boundary that falls inside a multi-byte UTF-8 character corrupts text.
// With it, Node's StringDecoder holds the partial character for you.
child.stdout.setEncoding("utf8");

child.stdout.on("data", (chunk: string) => {
  buffer += chunk;
  let newline: number;
  while ((newline = buffer.indexOf("\n")) >= 0) {
    const line = buffer.slice(0, newline);
    buffer = buffer.slice(newline + 1);
    if (line.trim()) onLine(line);
  }
  // A stream with no newline is either a non-protocol process or an
  // attack. Cap it rather than growing memory without bound.
  if (buffer.length > MAX_LINE) fail(new Error("oversized protocol line"));
});

The write direction has the mirror-image obligation. Because a newline terminates a message, your JSON must contain none: always JSON.stringify without an indent argument, and never hand-format a payload. One pretty-printed request turns into a dozen invalid lines and takes the connection down with it.

Test this deliberately

Feed your parser a captured session one byte at a time, then again in one giant chunk, then split at a random index inside a multi-byte character. All three must produce identical message sequences. This test catches more real bugs than any amount of end-to-end integration testing.

Dispatch

From a line to a meaning — and to a Promise or an event.

Once you have whole lines, every message goes down one of two paths. The choice is not stylistic: it follows from whether the message has a known recipient.

Known recipient → Promise

A response carries an id you issued. Exactly one caller is waiting, exactly once, and it needs the value or the error. That is a Promise, stored in a pending map keyed by ticket.

Unknown audience → event

A notification has no caller. Its audience is decided at runtime and may be zero listeners or five. That is an emission — fan-out, no return path, no settlement.

triage.ts
private onMessage(message: any) {
  // 1. id + (result|error) — a response to something WE sent.
  if ("id" in message && ("result" in message || "error" in message)) {
    const pending = this.pending.get(message.id);
    if (!pending) return this.emit("orphanResponse", message);  // timed out earlier
    clearTimeout(pending.timer);
    this.pending.delete(message.id);          // one settlement per ticket
    return message.error ? pending.reject(toError(message.error))
                          : pending.resolve(message.result);
  }

  // 2. id + method — the SERVER is asking us something and is blocked
  //    until we write back { id, result }. Approvals arrive here.
  if ("id" in message && message.method)
    return this.emit("serverRequest", message);

  // 3. method alone — a broadcast. No reply is possible.
  if (message.method) return this.emit("notification", message);

  // 4. None of the above. Never guess at intent.
  this.emit("protocolError", message);
}

Both sides issue ticket numbers independently, so the server's id: 61 and your id: 61 are unrelated. The discriminator is not the number but the shape: a message with id and method came from them; a message with id and result/error is an answer to you.

The serverRequest event has an obligation attached

Unlike a notification, dropping this one is not harmless — Codex is blocked on your reply and the turn will hang until it times out. Treat "serverRequest emitted with zero listeners" as a hard error and answer with an error envelope rather than letting it sit.

The write direction

Sending a query in: stdin is the only door.

All that read-side machinery has no counterpart on the write side. child.stdin is a Writable whose far end is the child's fd 0, and Codex sits in a loop reading lines from it. Sending a query means serializing one object, appending \n, and writing it.

A user's question is not a special message type. It is an ordinary turn/start request whose params.input happens to contain their text:

on-the-wire.jsonl
// This is the literal byte sequence written to the child's stdin.
// One line. No indentation. Newline-terminated.
{"id":3,"method":"turn/start","params":{"threadId":"thr_123","input":[{"type":"text","text":"What does this repo do?"}]}}
send-query.ts
export async function askCodex(
  rpc: AppServerRpc, threadId: string, userQuery: string, publish: (d: string) => void,
) {
  let finish!: (turn: unknown) => void, fail!: (e: Error) => void;
  const completed = new Promise((res, rej) => { finish = res; fail = rej; });

  // STEP 1 — Subscribe BEFORE writing. Deltas routinely arrive before the
  // turn/start response does; a listener attached after the await misses
  // them, and an emitter has no replay to recover from.
  const onNotification = (msg: any) => {
    if (msg.params?.threadId !== threadId) return;   // one process, many threads
    switch (msg.method) {
      case "item/agentMessage/delta": publish(msg.params.delta); break;
      case "turn/completed":           finish(msg.params.turn);  break;
      case "turn/failed":              fail(toError(msg.params)); break;
    }
  };
  rpc.on("notification", onNotification);

  try {
    // STEP 2 — The query. request() allocates ticket 3, stores
    // { resolve, reject, timer } in the pending map, and writes one line.
    const receipt = await rpc.request<{ turn: { id: string; status: string } }>(
      "turn/start", { threadId, input: [{ type: "text", text: userQuery }] },
    );

    // STEP 3 — receipt.turn.status === "inProgress". This Promise settled
    // when the RECEIPT arrived, not when Codex finished. The answer comes
    // through the emitter; the workflow ends on turn/completed.
    return { turnId: receipt.turn.id, result: await completed };
  } finally {
    // STEP 4 — Always unsubscribe. Per-turn listeners on a process-lifetime
    // emitter leak, and Node will warn at 11 of them.
    rpc.off("notification", onNotification);
  }
}

What else can go in input

The array is a union, so attachments are just more elements in the same single line of JSON (v2/turn.rs, lines 292–319):

mention{ type, name, path }File/symbol reference attached to the message.

The other three writes

  • Notification: { "method": "initialized" } — no id, so no Promise is registered and no reply ever comes.
  • Approval answer: { "id": 61, "result": { "decision": "accept" } } — echoes the server's ticket. Same pipe, same framing, opposite direction of the usual request.
  • child.stdin.end(): closes the pipe. Codex sees EOF on fd 0 and exits — your graceful-shutdown lever, and the reason a printf | codex app-server probe cannot wait out a streaming turn.

Backpressure and ordering

Node's Writable queues chunks internally, so two write() calls cannot interleave halfway through a line — a single write per message is already ordered. The promise chain in the transport earns its place for different reasons: it gives you an awaitable flush, propagates a write error back to the caller that caused it, and lets you respect the return value of write().

That return value matters under load. When the ~64 KB pipe buffer is full, write() returns false and Node starts queueing in your heap until a drain event fires. Ignoring it converts a slow child into unbounded memory growth in the parent. Ignoring the error event on stdin is worse: writing to a dead child raises EPIPE, and an unhandled stream error is an uncaught exception.

write-safely.ts
this.child.stdin.on("error", (error) => this.failAll(error));  // EPIPE lands here

private write(message: unknown) {
  if (this.child.exitCode !== null || this.child.stdin.destroyed)
    return Promise.reject(new Error("app-server is not running"));

  this.writeChain = this.writeChain.then(() => new Promise<void>((resolve, reject) => {
    // The callback fires once this chunk is flushed to the OS, so awaiting
    // the chain naturally paces writers against a full pipe buffer.
    this.child.stdin.write(`${JSON.stringify(message)}\n`,
      (error) => error ? reject(error) : resolve());
  }));
  return this.writeChain;
}

The one sentence to remember

Requests start work and return receipts; notifications tell the story; a terminal notification ends it. Anything that resolves on the turn/start response is measuring the wrong thing.

Scale

Many threads, one pipe, one emitter.

A single app-server process multiplexes every thread inside its isolation boundary, so notification is a firehose. The naive approach — each subscriber attaching its own listener and filtering by threadId — is O(clients × events) and re-derives the same projection work per client.

ThreadRouter.ts
export class ThreadRouter {
  private byThread = new Map<string, EventEmitter>();

  constructor(rpc: AppServerRpc) {
    // ONE listener on the firehose, forever. Dispatch is a Map lookup.
    rpc.on("notification", (msg) => {
      const threadId = msg.params?.threadId;
      if (!threadId) return this.global.emit(msg.method, msg.params);
      try {
        this.byThread.get(threadId)?.emit(msg.method, msg.params);
      } catch (error) {
        // A throwing listener must not unwind into the read loop and
        // kill protocol parsing for every OTHER thread on this process.
        logger.error({ error, threadId, method: msg.method }, "listener threw");
      }
    });
  }

  for(threadId: string) {
    let emitter = this.byThread.get(threadId);
    if (!emitter) this.byThread.set(threadId, emitter = new EventEmitter());
    return emitter;
  }

  release(threadId: string) {
    this.byThread.get(threadId)?.removeAllListeners();
    this.byThread.delete(threadId);   // or the Map grows forever
  }
}

Even so, per-client emitters are the wrong fan-out point for a product. Clients disconnect, reconnect, and need replay from a cursor — things an emitter fundamentally cannot provide. Route notifications into the session service's sequenced event log and let subscriptions read from that log, so a reconnecting tab resumes by sequence number instead of missing whatever was emitted while it was away.

Emitter, Promise, async iterator, or stream?

tRPC subscriptions want an async generator, so there is exactly one adapter at that boundary:

emitter-to-generator.ts
import { on } from "node:events";

async function* streamTurn(source: EventEmitter, signal: AbortSignal) {
  // on() attaches immediately and BUFFERS arrivals while the consumer is
  // awaiting — unbounded if the client is slow. Cap it, or shed deltas
  // under pressure and let the client resync from a snapshot.
  for await (const [params] of on(source, "item/agentMessage/delta", { signal })) {
    yield project(params);
  }
}
// The AbortSignal is the cleanup path: aborting detaches the listener,
// which is what makes "client closed the tab" stop costing you memory.
Reality

The child will die. Design for it.

A crash is not an exception you can catch — it is an event, arriving asynchronously, with in-flight Promises and blocked approvals attached to it.

1

error on the child

Spawn itself failed — binary missing, not executable, bad cwd. No exit follows. Must have a listener or Node throws it as uncaught.

2

exit — (code, signal)

The process is gone. Its stdio may still have buffered output not yet delivered to you.

3

close — after exit

All stdio is drained and closed. This is the safe point to conclude "no more messages are coming" — a late line can still arrive between exit and close.

4

Reject everything pending

Clear every timer, reject every entry in the pending map, and fail every unanswered serverRequest — a UI approval dialog whose process died must be dismissed, not left spinning.

5

Restart with backoff, then resume

Spawn a fresh process, redo the handshake, and reattach threads with thread/resume. Thread state persists in CODEX_HOME; your in-memory sequence numbers do not.

Kill the group, not the process

Codex spawns its own children (shells, build tools). child.kill() signals only the direct child, orphaning grandchildren that keep holding the workspace and CPU. Spawn detached: true and signal the negative PID to take down the whole process group, with SIGKILL on a timer as the backstop.

Field notes

Failure modes, ranked by how often they bite.

01

Subscribed too late

Listener attached after await request(…). The first deltas were emitted to an empty array and are unrecoverable. Fix: subscribe, then write.

02

Anonymous listener leak

on("notification", (m) => …) per turn can never be removed — off() compares by identity. Fix: named function, removed in finally.

03

Throwing listener kills parsing

emit() is synchronous, so the exception unwinds into the readline handler and every session on the process stops receiving messages. Fix: try/catch at the dispatch boundary.

04

Unhandled error event

An error emission with no listener is rethrown by Node and can take down the gateway. Fix: listeners on child, stdin, stdout; never emit "error" without a guaranteed listener.

05

Split-chunk parse crash

JSON.parse on a raw data chunk works in dev and fails under load, when messages get large enough to span chunks. Fix: readline or an explicit buffer.

06

Pretty-printed write

JSON.stringify(msg, null, 2) embeds newlines and shatters one message into many invalid lines. Fix: never pass an indent argument.

07

Resolving on the receipt

Treating the turn/start response as the answer. It only means "accepted". Fix: settle on turn/completed.

08

Async listener reordering

emit() does not await, so async listeners interleave and rejections vanish. Fix: enqueue, drain in order in one worker.

09

Ignored backpressure

write() returning false ignored, or events.on() buffering for a stalled client — both grow the heap silently. Fix: await flush; cap buffers and resync.

10

Orphaned serverRequest

An approval emitted with no listener leaves Codex blocked until timeout. Fix: treat zero listeners as an error and reply with an error envelope.

Tooling

Four things worth building on day one.

1. Tee every line to a file

The cheapest debugging tool in this stack. Both directions, with a monotonic timestamp and direction marker, gated behind a config flag and redacted. Every "it hung and nobody knows why" report becomes readable.

wire-tap.ts
rpc.on("notification", (m) => tap.write(`${Date.now()} <- ${JSON.stringify(m)}\n`));
rpc.on("serverRequest", (m) => tap.write(`${Date.now()} <- ${JSON.stringify(m)}\n`));
rpc.on("log",           (t) => tap.write(`${Date.now()} !! ${t}`));
// …and one line in write() for the -> direction.

2. A fake app-server

A ~40-line script that reads lines from stdin and prints canned responses gives you deterministic tests for the entire client: handshake ordering, streaming deltas, an approval that blocks, a mid-turn crash, a malformed line. No Codex binary, no model calls, no flakiness.

fake-app-server.mjs
import { createInterface } from "node:readline";
const send = (o) => process.stdout.write(JSON.stringify(o) + "\n");

createInterface({ input: process.stdin }).on("line", (line) => {
  const msg = JSON.parse(line);
  if (msg.method === "initialize") return send({ id: msg.id, result: { userAgent: "fake" } });
  if (msg.method === "turn/start") {
    send({ id: msg.id, result: { turn: { id: "t1", status: "inProgress" } } });
    // Deltas AFTER the receipt, on a later tick — the real ordering.
    setTimeout(() => send({ method: "item/agentMessage/delta",
      params: { threadId: msg.params.threadId, delta: "hello" } }), 5);
    setTimeout(() => send({ method: "turn/completed",
      params: { threadId: msg.params.threadId, turn: { id: "t1", status: "completed" } } }), 10);
  }
});

3. A byte-level parser fuzz

Replay a captured JSONL session through your parser at three granularities — one byte per chunk, whole file in one chunk, and random splits including inside multi-byte characters. Assert the emitted message sequence is identical in all three.

4. Listener-count gauges

Export listenerCount("notification"), pending.size, and the pending-approval count per process. All three should return to baseline when the system is idle. A sawtooth that never comes down is a leak you would otherwise find in production a week later.

  • Subscribe before writing; unsubscribe in finally
  • Named listener functions, never inline arrows for scoped subscriptions
  • try/catch at every dispatch boundary so one listener cannot kill the read loop
  • error listeners on the child and on both pipes
  • Reassemble lines; never JSON.parse a raw chunk
  • Compact JSON on write; one object, one newline
  • Settle workflows on terminal notifications, not RPC receipts
  • Reject pending work and dismiss pending approvals on close
  • Kill the process group, not just the child

Bottom line

An emitter is a subscription list. Subscribe before you write, unsubscribe in finally, and never let a listener throw into the read loop.

The one asymmetry

Responses settle Promises because they have one known recipient. Notifications become events because their audience is unknown at parse time.
