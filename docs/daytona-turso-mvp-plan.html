Summary

The Lightcode server remains the orchestration layer. It loads application state from Turso, ensures the project’s Daytona sandbox is available, launches a remote Codex turn, streams normalized events to the desktop, and persists the result.

DB

Turso owns state

Projects, threads, messages, sandbox mappings, and remote Codex thread IDs survive server restarts.

DX

Daytona owns execution

Codex, terminal commands, dependency installs, tests, and file changes run inside the remote sandbox.

API

Server owns orchestration

The existing tRPC stream stays stable while the execution driver changes from host-local to remote.

Execution boundary

The host server never runs the coding agent against the local project directory. Every agent tool action occurs in the Daytona sandbox.

Request lifecycle

Provisioning is lazy and idempotent. Normal messages reuse the existing project sandbox.

1

Load application state

Resolve the app thread, project, previous messages, Daytona sandbox ID, and external Codex thread ID from Turso.

2

Ensure the sandbox

Reuse or start the saved sandbox. If none exists, inspect the existing local Git project, create a TypeScript sandbox, clone its remote, and persist the mapping.

3

Start a remote turn

Create a unique Daytona PTY, run the uploaded agent package in the cloned repository, and start or resume the remote Codex thread.

4

Stream events

Parse newline-delimited agent events and translate them to the existing Lightcode notification shape for the desktop client.

5

Persist completion

Save assistant text, the remote Codex thread ID, timestamps, and turn outcome to Turso; then close the PTY and release the thread lock.

Recovery behavior

If Turso has a sandbox ID that Daytona no longer recognizes, clear the stale runtime mapping and reprovision. Preserve the project, chat, and message records.

Server implementation

Daytona workspace manager

  • Initialize one Daytona client from server configuration.
  • Create, resolve, start, and recover project sandboxes.
  • Clone the project and bootstrap the remote agent exactly once.
  • Use auto-stop so idle containers do not remain billable.

Remote agent package

  • Use the pinned @openai/codex-sdk.
  • Accept one validated JSON request per process.
  • Emit NDJSON records for deltas, final text, thread IDs, completion, and errors.
  • Apply model, reasoning, collaboration mode, and access settings.

Thread service

  • Load thread/project data from Turso.
  • Reject overlapping turns for the same app thread.
  • Persist user messages before remote execution.
  • Persist final assistant text and clear locks in finally.

Turn cancellation

  • Keep the active Daytona PTY handle by app thread ID.
  • Map stopTurn to termination of that PTY only.
  • Mark interruption distinctly from remote failure.
  • Never stop the shared project sandbox to cancel one chat.

Credentials and security

Keep execution isolated without placing durable credentials where agent-generated code can read them.

GitHub clone tokenLightcode server secret environmentPass transiently to the initial private clone API call; do not store in the sandbox or Turso.
!
No persistent Git authentication in v1

The sandbox may inspect and modify its clone, but it cannot fetch or push private repositories after provisioning. This matches the MVP decision to keep changes uncommitted and unpushed.

Scheduler decision

No scheduler for the MVP.

Provision or wake the sandbox synchronously when a message arrives. Configure Daytona auto-stop after 30–60 minutes of inactivity and let the next request restart it.

MVP lifecycle

message → Turso lookup → get/start sandbox → run turn → persist result

Add a scheduler later when needed

Use one only for proactive warm-up, cost enforcement, deletion of abandoned sandboxes, reconciliation, or scheduled background jobs.

Delivery phases

Implement vertical slices so each phase produces a testable boundary.

1

Turso persistence

Replace direct local SQLite access with a repository layer backed by libSQL, add additive migrations, and cover project/thread/message queries.

2

Sandbox provisioning

Add the Daytona client, project mapping, Git discovery, authenticated initial clone, bootstrap, reuse, and stale-sandbox recovery.

3

Remote Codex bridge

Upload the agent package, define its NDJSON protocol, run it over PTY, translate events, and persist external Codex thread IDs.

4

Lifecycle hardening

Add cancellation, per-thread locks, error classification, retry boundaries, configuration checks, and structured logs without secrets.

Test plan

Turso integration tests cover project/thread/message CRUD, ordering, remote ID persistence, and migrations.
Provisioning tests cover first creation, existing sandbox reuse, stopped sandbox restart, stale ID recovery, and failed bootstrap.
Git tests cover origin discovery, branch discovery, public clone, private clone, token redaction, and non-Git project errors.
Driver tests cover partial NDJSON chunks, multiple events per chunk, malformed records, stderr, non-zero exits, and stream completion.
Thread tests cover remote thread start/resume, message persistence, overlapping send rejection, interruption, and lock cleanup.
Acceptance test sends two turns to one chat, confirms the same sandbox and Codex thread are reused, and verifies file changes remain remote.
Workspace typechecks pass with the new Daytona and libSQL dependencies.

Assumptions and defaults

  • One durable Daytona sandbox per Lightcode project.
  • Separate external Codex thread ID per app chat.
  • Existing projects are Git repositories with an HTTPS origin.
  • Daytona TypeScript base image with first-use bootstrap.
  • Auto-stop after 30–60 idle minutes; no MVP scheduler.
  • No automatic commit, push, or local file synchronization.
  • No host-local fallback when Daytona fails.
  • Frontend tRPC streaming remains backward compatible.
