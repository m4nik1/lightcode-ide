Codex app-server behind tRPC.

A no-SDK integration design for an AI agent coding app: raw stdio JSONL at the process boundary, a typed bidirectional RPC multiplexer, and a stable domain API exposed through tRPC.

Recommended architecture TypeScript JSON-RPC-like tRPC subscriptions No app-server SDK
Executive decision

Use a process adapter, not a protocol pass-through.

Run codex app-server as a supervised child process using its default stdio transport. Keep its protocol private to your backend, translate it into a deliberately smaller tRPC contract, and stream normalized domain events to the app.

Recommended topology

Browser/Desktop UI → tRPC API + subscription → Agent Session Service → AppServerClient → codex app-server child process over newline-delimited JSON.

01

Production transport

Use stdio JSONL. WebSocket is explicitly experimental and unsupported for production.

02

Protocol ownership

Generate TypeScript from the exact Codex binary in CI, but expose your own stable frontend DTOs.

03

Process boundary

One long-lived process per isolation boundary, not one process per turn or per tRPC request.

04

Streaming model

Mutations initiate work; subscriptions carry ordered events. Terminal notifications settle app-level workflows.

What "no SDK" should mean

Do not hand-maintain hundreds of wire types. Using codex app-server generate-ts or generate-json-schema is schema generation, not an SDK dependency. It is the safest way to match the installed binary.

Primer

How the app-server JSON-RPC actually works.

If the previous section is the legal contract, this one is the guided tour. App-server speaks JSON-RPC 2.0 in everything but the version header: both sides exchange small JSON objects over one shared pipe, and four message shapes cover every conversation.

The mental model: a deli counter with ticket numbers

Think of the connection as a single phone line to a busy deli. There is no HTTP request/response pairing to lean on — just one stream of messages in each direction — so correlation is done with ticket numbers:

  • Request ({ id, method, params }): you place an order and take ticket id. Exactly one reply will eventually come back bearing that same ticket number. IDs can be strings or integers; the reply echoes whatever you sent.
  • Response ({ id, result } or { id, error }): your order arrives — or the counter tells you why it can't be filled. Never both, and never more than once per ticket.
  • Notification ({ method, params }, no id): the kitchen shouting status over the counter — "order 456 is on the grill". No ticket, no reply expected, and you cannot answer it.
  • Server request ({ id, method, params }, sent to you): the cook walks out and asks you a question — "this needs peanut oil, is that okay?" It carries the server's own ticket number, and the server blocks that piece of work until you write back { id, result }. This is how approvals work.

The one deliberate deviation from the JSON-RPC 2.0 spec: neither side sends the "jsonrpc":"2.0" field (rpc.rs states this in its first line). If your JSON-RPC library insists on adding or requiring it, don't use that library for this wire.

Framing: one JSON object, one line

Over the default stdio transport, the framing is newline-delimited JSON (JSONL) — like a chat where every message must be a single sentence with a period at the end. One compact JSON object, then \n. There are no Content-Length headers (unlike LSP), so a parser is just "split on newline, JSON.parse each line". The corollary: never pretty-print JSON when writing to stdin, because embedded newlines would split one message into several garbage lines.

A complete conversation, annotated

Here is an entire minimal session — handshake, thread, one turn — with direction markers. Everything marked → is written to app-server's stdin; ← arrives on its stdout.

annotated-session.jsonl
// 1. Handshake: one initialize request per connection, then the initialized notification.
→ {"method":"initialize","id":1,"params":{"clientInfo":{"name":"my_agent_server","title":"My Agent Server","version":"1.0.0"}}}
← {"id":1,"result":{"userAgent":"codex/…","codexHome":"/Users/me/.codex","platformFamily":"unix","platformOs":"macos"}}
→ {"method":"initialized"}   // notification: no id, no reply will come

// 2. Open a conversation. The response answers ticket 2; the notification is a broadcast.
→ {"method":"thread/start","id":2,"params":{"cwd":"/workspace/repo"}}
← {"id":2,"result":{"thread":{"id":"thr_123"},"model":"gpt-5.1-codex","cwd":"/workspace/repo"}}
← {"method":"thread/started","params":{"threadId":"thr_123"}}

// 3. Send a user message. The ticket-3 reply comes back immediately with an
//    in-progress turn — the actual work streams afterward as notifications.
→ {"method":"turn/start","id":3,"params":{"threadId":"thr_123","input":[{"type":"text","text":"What does this repo do?"}]}}
← {"id":3,"result":{"turn":{"id":"turn_456","status":"inProgress","items":[]}}}
← {"method":"turn/started","params":{"threadId":"thr_123","turn":{"id":"turn_456","status":"inProgress"}}}
← {"method":"item/started","params":{"threadId":"thr_123","turnId":"turn_456","item":{"type":"agentMessage","id":"item_1","text":""}}}
← {"method":"item/agentMessage/delta","params":{"threadId":"thr_123","turnId":"turn_456","itemId":"item_1","delta":"This repo is"}}
← {"method":"item/agentMessage/delta","params":{"threadId":"thr_123","turnId":"turn_456","itemId":"item_1","delta":" a CLI tool that…"}}
← {"method":"item/completed","params":{"threadId":"thr_123","turnId":"turn_456","item":{"type":"agentMessage","id":"item_1","text":"This repo is a CLI tool that…"}}}
← {"method":"turn/completed","params":{"threadId":"thr_123","turn":{"id":"turn_456","status":"completed"}}}

Notice the shape of the choreography: requests start things, notifications tell the story, and a terminal notification ends it. The turn/start response is a receipt, not a result — like a food-delivery app confirming your order was placed, while the courier updates stream in separately. Your code should resolve on turn/completed, not on the RPC response.

When the server asks you a question

The bidirectional part is what makes this feel different from a normal API. Mid-turn, app-server can send you a request with its own id, and the turn pauses until you answer:

server-initiated-request.jsonl
// Server -> client: note it has an id, so it is a request, not an event.
← {"method":"item/commandExecution/requestApproval","id":61,"params":{"threadId":"thr_123","turnId":"turn_456","itemId":"item_9","command":"npm install","cwd":"/workspace/repo","reason":"Needs network access"}}

// Client -> server: a plain response envelope, echoing the server's id 61.
→ {"id":61,"result":{"decision":"accept"}}

Because both sides hand out ticket numbers independently, your ID counter and the server's can overlap without conflict — id: 61 from the server and id: 61 from you are different tickets, distinguished by who issued them. Classify each incoming line by shape: id + result/error is a response to you; id + method is a question for you; method alone is a broadcast.

Ways to poke at it

Because the transport is just lines of JSON on stdio, you can explore the protocol with nothing but a terminal before writing any client code.

This works for read-only probes, but stdin closes as soon as printf finishes, so it can't wait out a streaming turn. For that, use the interactive form or a real client.

3. A real client: spawn and correlate

Spawn the process from your backend, split stdout on newlines, and keep a Map of pending tickets — the full implementation is the AppServerRpc class in the transport section. The essential loop fits in a few lines:

essence.ts
const child = spawn("codex", ["app-server"]);
createInterface({ input: child.stdout }).on("line", (line) => {
  const msg = JSON.parse(line);
  if (msg.id !== undefined && msg.method === undefined) settlePending(msg);   // response to us
  else if (msg.id !== undefined) answerServerRequest(msg);                    // question for us
  else handleNotification(msg);                                               // broadcast
});
child.stdin.write(JSON.stringify({ id: 1, method: "initialize", params }) + "\n");

4. Other transports

  • Unix socket: codex app-server proxy bridges stdin/stdout to a running server's control socket at $CODEX_HOME/app-server-control/app-server-control.sock — useful for attaching a second tool to an already-running server.
  • WebSocket: --listen ws://IP:PORT puts one JSON-RPC message per text frame and serves /readyz//healthz probes, but it is explicitly experimental and unsupported — fine for a spike, wrong for production.
  • Typed exploration: codex app-server generate-ts --out DIR dumps the full method/notification catalog as TypeScript unions for the exact binary you have installed — the closest thing to browsable API docs, generated from source of truth.
The four-question triage for any incoming line

Has result or error plus id? It settles one of your tickets. Has method plus id? The server is asking; you must eventually write back that id. Has only method? File it as an event. None of the above? Log it as a protocol fault — don't guess.

Process granularity

The right process boundary depends on whose credentials, config, and filesystem the process can see:

  • Single-user local/desktop app: one process for the backend lifetime is simplest.
  • Hosted workspace product: one process per isolated workspace, container, VM, or user security boundary.
  • Do not share across untrusted tenants: CODEX_HOME, login state, config, stored threads, MCP configuration, and filesystem authority make a globally shared process unsafe.
  • Do not spawn per turn: initialization, loaded threads, subscriptions, credentials, MCP startup, and session state are process-oriented.
Connection choreography

Initialize once, then drive threads and turns.

Spawn

Start codex app-server with piped stdin/stdout. Keep stderr separate for logs; never merge it into protocol stdout.

2

Initialize

Send exactly one initialize request with honest client metadata. Wait for its response.

3

Acknowledge

Send the initialized notification. Requests before initialization fail; repeated initialization fails.

4

Mechanics

Event emitters, pipes, and how a query reaches Codex.

The transport class below extends EventEmitter and talks to a spawned child process. Those two ideas carry most of the design, so this section unpacks them before the code: what an emitter actually is, why a spawned process forces you to use one, and the exact path a user's question takes from a tRPC call into codex app-server and back.

What an event emitter is

An EventEmitter is a subscription list. That is the whole idea — it is not a queue, not a channel, not a message bus with delivery guarantees. Stripped down, it is an object holding a map from event names to arrays of functions, plus two methods: one that appends a function to an array, and one that walks an array and calls every function in it.

emitter-basics.ts
import { EventEmitter } from "node:events";

const bus = new EventEmitter();

// on() only stores the function. Nothing runs yet, and there is no
// registry of valid event names — "delta" is just a string key.
bus.on("delta", (text) => process.stdout.write(text));
bus.on("delta", (text) => transcript.push(text));   // many listeners per event

// emit() looks up the array and calls each function, in registration
// order, synchronously, before emit() itself returns.
bus.emit("delta", "This repo is");   // => true  (a listener existed)
bus.emit("nobodyHome", 42);            // => false (dropped silently)

bus.once("exit", cleanup);              // auto-removes after first call
bus.off("delta", transcriptListener);   // you must remove what you add

Four consequences follow directly from that implementation, and every bug in this layer traces back to one of them:

  • Emission is synchronous and fire-and-forget. emit() returns a boolean meaning "someone was listening", never a value from a listener. If a listener is async, the emitter does not await it — it gets a floating promise and moves on.
  • There is no history. A listener registered after an emit() never sees that emission. Subscribe first, act second — this is the single most common cause of "the first few tokens are missing".
  • There is no backpressure. The emitter cannot tell a fast producer to slow down. If Codex streams deltas faster than your tRPC subscription drains them, buffering is your problem to solve.
  • A throwing listener escapes upward. Because the call is synchronous, an exception propagates out of emit() into whatever called it — here, the readline line handler that parses the protocol.

Emitters exist because a stream of arrivals has no natural place to return to. A function call is one question and one answer; a child process spitting out tokens for ninety seconds is neither. The emitter inverts control: instead of your code asking "what happened next?", you leave callbacks behind and the runtime calls them as things happen.

Why spawning a process forces you into this shape

spawn(codexBinary, ["app-server"], { stdio: ["pipe", "pipe", "pipe"] }) asks the OS for three pipes and starts a genuinely separate program. The child gets the far ends as file descriptors 0, 1, and 2; your Node process gets the near ends as stream objects. Codex has no shared memory with you, no function you can call, and no return value to hand back — the only channel is bytes in a pipe, arriving whenever the kernel says so. Node surfaces that arrival the only way it can: as events.

So you inherit a chain of emitters before writing a single line of your own. child is an emitter (spawn, exit, error, close). child.stdout is a Readable, which is an emitter (data, end). The readline Interface wrapped around it is an emitter too (line, close). AppServerRpc extends EventEmitter to add one more link on the end — and that last link is the one that carries meaning rather than plumbing.

child.stdoutOS pipe. Emits data with whatever Buffer chunk the kernel delivered — a half line, three lines, or one byte. No message boundaries.
→
readline InterfaceBuffers chunks and emits line exactly once per \n. This is what turns a byte stream back into discrete JSON messages.
→
AppServerRpcJSON.parse, then triage by envelope shape: settle a pending Promise, or emit notification / serverRequest / log / exit.

That final triage is the interesting part, and it is where two different concurrency primitives split apart. A response has exactly one arrival and belongs to one caller, so it settles a Promise held in the pending map. A notification has no caller — it is a broadcast whose audience is unknown at parse time and may include the session projector, a logger, and three subscribed browser tabs — so it is re-emitted as an event. Same wire, same parse, different delivery mechanism, chosen by whether the message has a known recipient.

Sending data in: stdin is the only door

Everything above is the read direction. Writing is simpler and almost anticlimactic: child.stdin is a Writable whose other end is the child's fd 0. Codex sits in a loop reading lines from it. To send a query you serialize one JSON object, append \n, and write it. There is no API, no socket, no handshake per message — the newline is the message boundary, which is why a pretty-printed payload corrupts the stream: every embedded newline is read as the end of a message.

A user's question is not a special kind of write. It is an ordinary turn/start request whose params.input carries the text:

send-query.ts
// STEP 1 — Subscribe before sending. Deltas can arrive before the
// turn/start response does; a listener attached afterward misses them.
const onNotification = (msg: any) => {
  if (msg.params?.threadId !== threadId) return;   // one process, many threads
  switch (msg.method) {
    case "item/agentMessage/delta": publish(msg.params.delta); break;
    case "turn/completed":           finish(msg.params.turn);  break;
    case "turn/failed":              fail(msg.params);         break;
  }
};
rpc.on("notification", onNotification);

try {
  // STEP 2 — The query itself. request() allocates ticket id N, stores
  // { resolve, reject } in the pending map, and writes ONE line to stdin:
  //   {"id":3,"method":"turn/start","params":{…}}\n
  const receipt = await rpc.request<{ turn: { id: string; status: string } }>(
    "turn/start",
    {
      threadId,                                        // from thread/start
      input: [{ type: "text", text: userQuery }],     // the actual question
    },
  );

  // STEP 3 — receipt.turn.status is "inProgress". This Promise settled
  // when the RECEIPT came back, not when Codex finished thinking. The
  // answer arrives on the emitter, and completion is turn/completed.
  await completionPromise;
} finally {
  // STEP 4 — Always unsubscribe. Per-turn listeners on a long-lived
  // emitter are a memory leak with a warning attached (see below).
  rpc.off("notification", onNotification);
}

The input array is a union, not just text — { type: "image", url }, { type: "localImage", path }, { type: "skill", name, path }, and { type: "mention", name, path } are the other members (v2/turn.rs, lines 292–319). An attachment is just another element in the same array, in the same single line of JSON.

Three writes matter beyond queries, and all use the identical mechanism: a notification ({ method }, no id) for handshake acknowledgement, an approval answer ({ id, result } echoing the server's ticket), and child.stdin.end(), which closes the pipe and makes app-server exit. That last one is your graceful-shutdown lever — and also the reason the printf | codex app-server probe in the protocol section cannot wait out a streaming turn: printf finishes, stdin closes, the server shuts down mid-answer.

The full round trip

1

tRPC mutation arrives

agent.sendMessage({ sessionId, text }). The session service resolves the tenant's thread ID and picks the owning process.

2

One line onto stdin

request("turn/start", …) registers pending ticket 3, then writes {"id":3,"method":"turn/start","params":{…}}\n into the pipe. The mutation returns the receipt.

3

Kernel delivers chunks back

Codex writes JSON lines to its fd 1. child.stdout emits data Buffers with arbitrary boundaries; readline reassembles them into whole lines.

4

Triage per line

Ticket 3's response resolves the Promise. Every item/* and turn/* line becomes an emitted notification.

5

Project and fan out

Listeners normalize each notification into a sequenced session event, append it to the replay buffer, and push it to every subscribed client.

6

Settle on the terminal event

turn/completed ends the workflow and the per-turn listeners are removed. If an approval interrupted the turn, a serverRequest was answered on the same stdin pipe along the way.

Handing an emitter to tRPC

tRPC subscriptions consume async generators, not emitters, so there is one adapter at the boundary. events.on() converts an emitter into an async iterable, which lets you write the stream as a loop with a natural return and abort-signal cleanup:

emitter-to-generator.ts
import { on } from "node:events";

async function* streamTurn(rpc: AppServerRpc, threadId: string, signal: AbortSignal) {
  // on() attaches the listener immediately and buffers arrivals while the
  // consumer is awaiting — an UNBOUNDED buffer if your client is slow.
  // Cap it, or drop deltas under pressure and resync from a snapshot.
  for await (const [msg] of on(rpc, "notification", { signal })) {
    if (msg.params?.threadId !== threadId) continue;
    if (msg.method === "item/agentMessage/delta") yield project(msg);
    if (msg.method === "turn/completed") return;   // listener detached here
  }
}

Do not put this adapter directly on AppServerRpc per connected client. Every subscriber filtering the full notification firehose by thread ID is O(clients × events) and re-derives projection work. Fan out from the session service's already-normalized, already-sequenced event log instead, which is what the events section describes.

Emitter failure modes to design against

An error event with no listener is rethrown by Node and can take down the process — always attach child.on("error", …), and never emit "error" from your own class without a guaranteed listener. Because emit() is synchronous and unguarded, a listener that throws unwinds into the readline handler and can kill protocol parsing for every session on that process: wrap listener bodies in try/catch. Node warns at 11 listeners on one event name (MaxListenersExceededWarning); if you see it, you are leaking per-turn or per-client subscriptions that were never removed.

On the write chain in the sample below

A single stdin.write() per line is already ordered — Node's Writable queues chunks internally, so two calls cannot interleave halfway through a line. The promise chain earns its place for the other reasons: it gives you an awaitable flush, propagates write errors to the caller that caused them, and respects backpressure when the ~64 KB pipe buffer fills instead of growing an unbounded in-memory queue.

Implementation blueprint

A minimal bidirectional RPC client.

This is intentionally a thin wire layer. It knows envelopes and correlation, but not product policy.

AppServerRpc.ts
import { spawn, type ChildProcessWithoutNullStreams } from "node:child_process";
import { createInterface } from "node:readline";
import { EventEmitter } from "node:events";

type Id = string | number;
type Pending = {
  resolve(value: unknown): void;
  reject(error: Error): void;
  timer: NodeJS.Timeout;
};

export class AppServerRpc extends EventEmitter {
  private child!: ChildProcessWithoutNullStreams;
  private nextId = 1;
  private pending = new Map<Id, Pending>();
  private writeChain = Promise.resolve();

  async start(codexBinary = "codex") {
    // The default app-server listener is stdio://.
    this.child = spawn(codexBinary, ["app-server"], {
      stdio: ["pipe", "pipe", "pipe"],
      env: { ...process.env },
    });

    createInterface({ input: this.child.stdout }).on("line", (line) => {
      if (!line.trim()) return;
      this.onMessage(JSON.parse(line));
    });
    this.child.stderr.on("data", (chunk) =>
      this.emit("log", chunk.toString()),
    );
    this.child.once("exit", (code, signal) =>
      this.failAll(new Error(`app-server exited: ${code ?? signal}`)),
    );

    await this.request("initialize", {
      clientInfo: { name: "my_agent_server", title: "My Agent Server", version: "1.0.0" },
      capabilities: { experimentalApi: false },
    });
    await this.notify("initialized");
  }

  request<T>(method: string, params?: unknown, timeoutMs = 30_000): Promise<T> {
    const id = this.nextId++;
    return new Promise<T>((resolve, reject) => {
      const timer = setTimeout(() => {
        this.pending.delete(id);
        reject(new Error(`app-server timeout: ${method}`));
      }, timeoutMs);
      this.pending.set(id, { resolve: resolve as (v: unknown) => void, reject, timer });
      this.write({ id, method, ...(params === undefined ? {} : { params }) }).catch(reject);
    });
  }

  notify(method: string, params?: unknown) {
    return this.write({ method, ...(params === undefined ? {} : { params }) });
  }

  respond(id: Id, result: unknown) { return this.write({ id, result }); }
  respondError(id: Id, code: number, message: string, data?: unknown) {
    return this.write({ id, error: { code, message, ...(data === undefined ? {} : { data }) } });
  }

  private onMessage(message: any) {
    if ("id" in message && ("result" in message || "error" in message)) {
      const pending = this.pending.get(message.id);
      if (!pending) return this.emit("orphanResponse", message);
      clearTimeout(pending.timer);
      this.pending.delete(message.id);
      return message.error
        ? pending.reject(Object.assign(new Error(message.error.message), message.error))
        : pending.resolve(message.result);
    }
    if ("id" in message && message.method)
      return this.emit("serverRequest", message);
    if (message.method) return this.emit("notification", message);
    this.emit("protocolError", message);
  }

  private write(message: unknown) {
    // Serialize writers so JSON lines cannot interleave.
    this.writeChain = this.writeChain.then(() => new Promise<void>((resolve, reject) => {
      this.child.stdin.write(`${JSON.stringify(message)}\n`, (error) => error ? reject(error) : resolve());
    }));
    return this.writeChain;
  }

  private failAll(error: Error) {
    for (const pending of this.pending.values()) {
      clearTimeout(pending.timer); pending.reject(error);
    }
    this.pending.clear();
    this.emit("exit", error);
  }
}
Production hardening omitted from the sample

Add envelope validation, maximum line size, startup/idle/operation-specific timeouts, abort signals, graceful shutdown, process-group termination, secret redaction, metrics, and restart policy. If a write fails after adding a pending entry, remove and reject that entry immediately.

Use a separate public session ID instead of exposing threadId as your authorization boundary. Store the mapping { publicSessionId, tenantId, workspaceId, appServerInstanceId, threadId } server-side.

Streaming and projection

Normalize once; replay by sequence.

Raw notifications are transport events, not a durable frontend state model. Convert them into a compact product event union and assign a monotonically increasing sequence number per session.

AgentEvent.ts
type AgentEvent =
  | { seq: number; type: "turn.started"; turnId: string }
  | { seq: number; type: "item.started"; turnId: string; item: AgentItem }
  | { seq: number; type: "item.delta"; turnId: string; itemId: string; channel: "message" | "reasoning" | "command"; delta: string }
  | { seq: number; type: "item.completed"; turnId: string; item: AgentItem }
  | { seq: number; type: "approval.requested"; request: ApprovalRequest }
  | { seq: number; type: "request.resolved"; requestId: string | number }
  | { seq: number; type: "turn.completed"; turnId: string; status: "completed" | "interrupted" | "failed"; error?: AgentError }
  | { seq: number; type: "session.resyncRequired"; reason: string };

Projection rules

  • On item/started, insert the item by item.id.
  • Append deltas in arrival order, keyed by threadId + turnId + itemId.
  • On item/completed, replace the in-progress item with the full final item.
  • Use turn/diff/updated as the latest full diff snapshot; do not concatenate these values.
  • Use turn/plan/updated as the current plan snapshot.
  • On turn/completed, finalize the turn even if an earlier error notification was shown.
  • Deduplicate by your event sequence, not by payload equality. Delta text may legitimately repeat.

Reconnect strategy

The tRPC subscription input should include after, the last sequence applied by the client. Replay buffered/persisted events newer than that cursor, then switch to live delivery. If the cursor is too old, send a snapshot plus a new base sequence or emit session.resyncRequired.

Do not let a slow browser backpressure app-server stdout

The gateway must continuously drain app-server output into bounded internal queues. Coalesce high-volume deltas or disconnect/resync a slow subscriber. A browser's network speed must never block protocol reading.

Bidirectional flows

Approvals are pending RPCs, not events alone.

When app-server asks the client a question, retain the original app-server request ID. Publish a safe UI representation, then use the user's tRPC mutation to answer that exact ID.

1

Receive inbound request

Classify by method, validate params, and associate it with the owning thread/session.

2

Store pending state

Persist an opaque public request token mapped to the raw app-server request ID. Never trust a client-supplied thread mapping.

3

Publish UI event

Send the proposed command/diff, reason, available decisions, and timeout metadata through the session subscription.

4

Authorize and answer

Check ownership, allowed choice, single-resolution state, and request freshness; then write { id, result }.

5

Close pending UI

Consume serverRequest/resolved. It can also arrive when turn start/completion/interruption clears an unanswered request.

Failure model

Make crashes explicit and recovery bounded.

FailureRequired behavior
Malformed stdout lineCapture redacted diagnostics, count a protocol fault, and restart after a conservative threshold. Do not silently skip arbitrary protocol corruption.

RestartPerform a fresh initialize handshake, then thread/resume active persisted threads to restore subscriptions. Ephemeral threads cannot be recovered.

Idempotency and reconciliation

  • Send a unique clientUserMessageId and store it with the product message. It is echoed on the corresponding user item, which helps reconciliation.
  • A transport failure after writing turn/start is ambiguous. Before retrying, read/resume the thread and look for the client message ID.
  • Use your own idempotency key for sendMessage and serialize turn starts per thread.
  • Reject a second approval response locally; server requests are single-settlement.
  • On shutdown, stop accepting turns, interrupt or drain active work according to policy, unsubscribe where useful, close stdin, then enforce a deadline before killing the child.

Observability

Log structured metadata, not raw secrets: process instance ID, request ID, method, thread/turn/item IDs, latency, result class, queue depth, restart count, event lag, and tRPC correlation ID. Set LOG_FORMAT=json for app-server stderr and ingest it as a separate log stream. Redact API keys, auth URLs/tokens, user prompts where policy requires, command environment, dynamic tool arguments, and file contents.

Trust boundaries

Treat the gateway as a privileged local agent.

App-server can execute commands, edit and read files, mutate config, authenticate accounts, invoke MCP tools, and run unsandboxed thread shell commands. Your tRPC layer must narrow that authority.

  • Resolve each workspace root server-side and canonicalize it; never accept an arbitrary browser-provided cwd.
  • Enforce tenant/user ownership on every session, event subscription, turn, and approval response.
  • Run app-server under an OS/container identity scoped to the workspace. Sandbox policy is defense in depth, not tenant isolation.
  • Do not expose generic fs/*, config/*, account/*, process/*, or thread/shellCommand procedures unless your product explicitly needs and authorizes them.
  • Keep approvalPolicy conservative. Never let an untrusted frontend silently switch to never or full access.
  • Bind pending server requests to session + user + process instance + original request ID; use one-time opaque public tokens.
  • Separate CODEX_HOME by isolation boundary and protect persisted credentials/config with filesystem permissions and encrypted storage where applicable.
  • Validate image/data URL size and type. Remote HTTP(S) image URLs are rejected by app-server; prefer controlled uploads followed by local paths.
  • Rate-limit turn starts, large inputs, process creation, approvals, and subscriptions.
  • Opt into experimental APIs only for specific features you own and test. Experimental methods and fields have no compatibility guarantee.
Avoid the unsandboxed shortcut

thread/shellCommand runs user-initiated shell commands unsandboxed with full access. Do not map it to a general browser terminal. If you need utilities, prefer a narrowly validated product operation or the sandboxed command/exec surface.

Authentication model

App-server supports API key, ChatGPT-managed OAuth/device flow, personal access token, and experimental managed Bedrock auth. For a local app, let app-server own ChatGPT OAuth and token refresh. For hosted multi-user infrastructure, isolate credential stores per user/workspace and decide whether credentials are user-owned or service-owned before choosing process granularity. Query account/read after initialization and expose only the minimal account state your UI needs.

clientInfo.name identifies the integration in enterprise compliance logs. Use an honest stable identifier; the app-server documentation asks enterprise integrations to coordinate registration as a known client.

Definition of done for v1

  • A user can start/resume a persisted coding session and send a text turn.
  • The UI renders agent text, command progress/output, file changes, and terminal status from normalized events.
  • Command and file approvals work bidirectionally and cannot be answered by another user/session.
  • A browser reconnect resumes from an event cursor without duplicating visible output.
  • An app-server crash rejects ambiguous operations, restarts, reinitializes, and resumes recoverable threads.
  • All filesystem access is constrained to a server-resolved workspace isolation boundary.
  • The deployed Codex binary and generated protocol schema are version-locked.

Bottom line

Use stdio. Hide raw methods. Normalize events. Treat approvals as bidirectional RPC. Pin schema to binary.

Primary risk

A shared app-server process is a credential, config, conversation, and filesystem trust boundary.

Protocol status

Stable v2 surfaces are preferred. WebSocket and several advanced methods are experimental.
